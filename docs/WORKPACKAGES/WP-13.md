## What to build

- `examples/next-app/`: a minimal Next.js App Router app using the kit
  exactly as PLAN §11: `globals.css` with the tokens and `@source`,
  `layout.tsx` with `fontClassName`, `ThemeProvider` (brand from env),
  `I18nProvider` (language from cookie and `Accept-Language`),
  `eslint.config.js` extending `/eslint`, the four BFF routes via
  `bffHandlers` pointed at a stub API (an in-repo route handler that
  mimics login and a `GET /v1/zones` serving the fixture ED-318
  collection with an `ETag`, so the example runs without a system), a
  `src/api/generated/openapi.d.ts` generated with `uspace-ui-gen-api`
  from `examples/next-app/openapi.yaml` (a tiny OpenAPI 3.1 file with
  the zones endpoint and the login endpoint), a public map page
  (`MapView` + `ZoneLayer` + `ZoneLegend` + `MapControls`, zones fetched
  through the client with `freshnessOf` and shown as "version V,
  updated T"), a sign-in page with `LoginForm`, a protected page with
  `RequireRole`, the CSP of PLAN §7 in `next.config`, `output:
  "standalone"`, a `Dockerfile` that copies the standalone output (so a
  system's image recipe is documented here once). Both languages via
  the language switch.
- `release.yml`: on tag `v*`: checkout, pnpm, the `check`, `test`,
  `browser`, `fonts` jobs (reuse via `workflow_call` from `ci.yml` or a
  composite action; no duplicated steps), assert `package.json`
  `version` equals the tag, `pnpm publish --provenance --access public`
  with `permissions: id-token: write`, then a GitHub release whose body
  is the CHANGELOG section for the version (a script extracts it;
  fails if the section is missing).
- `pages.yml`: on push to `main` with the path filter of PLAN §10,
  `storybook build` and `actions/deploy-pages`; `concurrency` so only
  the latest deploys.
- `docs/CONSUMING.md`: the step list for a `web/` (install, CSS,
  layout, lint, BFF, generated types, adapters, the basemap bundle
  path, the CSP, the Docker recipe, the upgrade policy of PLAN §11,
  §12). `README.md` links it and states the status and the Pages URL.
- `CHANGELOG.md` `0.1.0` section listing the entry points shipped and
  the ones not yet (so a consumer does not look for `live` in 0.1).
- First publish: a dry run (`pnpm publish --dry-run`) in the PR with the
  file list pasted; the real publish happens when the owner tags
  `v0.1.0` from `main`.

## Safety notes

Nothing here judges, but everything here is the supply chain of four
state consoles (`06 §4`): the publish must be reproducible from a tag,
signed by the workflow, and contain only built output. A release that
quietly includes `stories/` fixtures or a `.env` would ship test data
into an image; the pack test is the guard. The stub API in the example
is a stub for the example only and never a template for a system's
API: its `README.md` says so.
