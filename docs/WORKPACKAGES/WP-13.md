## What to build

- `examples/next-app/`: a minimal Next.js App Router app using the kit
  exactly as PLAN §11: `globals.css` with the tokens and `@source`,
  `layout.tsx` with `fontClassName`, `ThemeProvider` (brand from env),
  `I18nProvider` (language from cookie and `Accept-Language`),
  `eslint.config.js` extending `/eslint`, the three BFF routes via
  `bffHandlers` pointed at a stub API (an in-repo route handler that
  mimics login, issuing a session JWT in the reconciled shape with
  `roles: [...]` and `realm: "console"`, and a `GET /v1/zones` serving
  the fixture ED-318 collection with an `ETag` and `cis_updated_at`,
  so the example runs without a system; the stub honours
  `?applies_at=` by annotating `cis_applicability` on the fixture), a
  `src/api/generated/openapi.d.ts` generated with `uspace-ui-gen-api`
  from `examples/next-app/openapi.yaml` (a tiny OpenAPI 3.1 file with
  the zones endpoint and the login endpoint), a public map page
  (`MapView` + `ZoneLayer` + `ZoneLegend` + `MapControls`, zones fetched
  through the client with `freshnessOf` and shown as "version V,
  updated T"), a sign-in page with `LoginForm`, a protected page with
  `RequireRole`, the CSP of PLAN §7 in `next.config`, `output:
  "standalone"`, a `Dockerfile` that copies the standalone output and
  installs with `pnpm install --frozen-lockfile` from the committed
  `pnpm-lock.yaml` (so a system's image recipe is documented here
  once; no `npm ci`, no `prepare` build of the kit inside the image:
  the kit is a published tarball from npmjs). The example's `web/`
  does not serve a basemap: `BasemapConfig.baseUrl` is `/basemap/` and
  the `README.md` says the deployment's Caddy serves it from the shared
  volume; for the smoke test, `next.config` rewrites `/basemap/*` to
  the browser tests' extract under `browser/public/basemap/`. Both languages via
  the language switch. The example opens no WebSocket in `0.1.0`
  (`live` is `0.2.0`); a comment in the layout says the WS will be
  opened same-origin on the session cookie, never with a ticket.
- `docs/CONSUMING.md`: the step list for a `web/` (pnpm with
  `packageManager` pinned and `--frozen-lockfile`; install from npmjs
  with an exact pin, rc versions under the `next` dist-tag; CSS;
  layout with `next/font/local`; lint; the three BFF routes and the
  cookie names; the same-origin WebSocket on the cookie; generated
  types; adapters, including `cis_applicability` → `applies`; the
  basemap bundle path served by `uspace-deploy`; the CSP; the Docker
  recipe; the upgrade policy of PLAN §11, §12; the minimum version per
  consumer of PLAN §11). `README.md` links it and states the status.
- `CHANGELOG.md` `0.1.0` section listing the entry points shipped and
  the ones not yet (so a consumer does not look for `live` in 0.1), and
  what changed since the last `0.1.0-rc.N`.
- The stable tag: the owner tags `v0.1.0` from `main`; WP-13a's
  `release.yml` publishes it under `latest` (no pre-release suffix, so
  no `--tag next`).

## Safety notes

Nothing here judges, but everything here is the supply chain of four
state consoles (`06 §4`): the publish must be reproducible from a tag,
signed by the workflow, and contain only built output. A release that
quietly includes `browser/` fixtures or a `.env` would ship test data
into an image; the pack test is the guard. The stub API in the example
is a stub for the example only and never a template for a system's
API: its `README.md` says so.
